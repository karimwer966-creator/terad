## Pipeline and rejection points

Source citations are `nadir2.mq5` unless otherwise marked; line numbers correspond to this branch. The map describes the CORE path, not the independent ZRE or display-only RXN path.

```text
MT5 chart OHLC/time/spread + ATR/ADX/RSI + multi-timeframe history
  -> OnCalculate (15582; chronological g_buf arrays, closed = rates_total-2)
  -> DetectStructure / DetectLiquidity / DetectOrderBlocks / DetectFVG
  -> BuildCausalEventGraph (17048): pool -> sweep -> displacement -> structure -> OB/FVG
  -> SelectBestStructureAnchor (17998) -> CalculateAITradeSetup (20604)

```

## Gate values and order

The values in the request (55 confidence, 60 reliability, 1.30 TopDown RR and 3 ATR stop) are **not the compiled defaults in this checkout**. `nadir2.mq5:1040–1046,1199–1213,1377–1389` specifies STRICT by default, confidence **75**, reliability **80**, CORE RR1 **1.50**, max stop **4.0 ATR**, TopDown RR **2.00**, TopDown confluences **3**. STRICT uses the inputs via `Eff*` functions (`:19394`); writable config shadows may heal invalid inputs (`:14835`). The EA's `iCustom` call passes no input list (`EA:3701`): a preset on a separately attached visible indicator does not configure the EA's reader. Verify the actual compiled reader's initialization banner and instance identity; a slot probe is not proof of version or semantic mapping.

For a selected CORE candidate the source order is location/direction/proximity/blacklist/spread → conditional TopDown veto → stop/target geometry → confidence → conditional EMA/VWAP → CORE RR1 → optional grade → reliability → transactional causal branch → retest/confirmation. TopDown's own RR and confluences apply to its separate M5 plan, not automatically to CORE's TP1. With `InpRequireInstitutionalConfirm=false`, a failed TopDown verdict is not itself a hard veto. No claim is made that TopDown can never affect other scoring or grade paths. The exact rejecting gate for the reported incident remains **unknown** without the reader's per-instance evidence.

## Readiness, history and direction audit

- The EA creates a handle with `iCustom`, checks the reader handshake, may release/retry the handle, and releases it on deinit. It probes slots and `BarsCalculated` (`EA:2497`); successful copies verify slot accessibility, **not** build identity, payload correctness, or upstream completeness.
- The indicator uses non-series chronological buffers (`:15053`); `SigLog_PrepareBuffers` (`:14285`) zeroes the full range on reset or the newly allocated tail, then replays this instance's registered signals by bar time. Its in-memory registry is bounded at 20,000 entries and compacts to half; retention across indicator reinitialization is not guaranteed. New bars can be zero before publication. Refresh or changed history within the same initialized instance is intended to reapply registered records, but MT5 runtime verification is outstanding.
- In `OnCalculate`, `prev_calculated==0` triggers full preparation; market detection can rebuild history but CORE setup evaluation is called for the **current** closed bar (`:16054`), not a historical trade-signal replay. This is why zero-filled older buffers cannot be read as a backtest.
- The six EA arrays use `ArraySetAsSeries(...,true)`; the EA's loop excludes shift 0. `CopyBuffer` copies are required to return the requested count, but there is no explicit guarantee that all upstream indicator inputs completed; the indicator continues after bounded incomplete-copy retries. TopDown's `CopyRates` accepts partial history when it has at least four closed bars (`:33131`); no blanket `SERIES_SYNCHRONIZED` proof is present on this path.
- **Source defect corrected:** `EMPTY_VALUE` can be a finite sentinel; the old polling code checked direction only for zero, and checked price sentinels but not the direction sentinel before converting its sign. Invalid/non-ABI directions could be treated as BUY/SELL. The EA now refuses any nonzero direction other than exact +1/-1 before expiry or order handling, with a separate in-memory diagnostic dedup ring so it does not mark a legitimate BUY/SELL as seen. Other signal semantics and risk/authorization controls are unchanged. MT5 verification remains required.
- The diagnostic heartbeat now requires enough calculated bars and a full copy for its window, counts exactly shifts 1..N, and reports invalid directions as **indeterminate**, not zero. This is not a complete readiness guarantee: zero-filled buffers may still be observed after upstream copy retries are exhausted. Export history is explicitly qualified as session-scoped.

## Statistics and diagnostic coverage

**Actual rejection statistics: BLOCKED**, because there is no matching reader log or runtime trace. `SSignalGateAudit` (`:3800`) and `GateAuditReject` (`:19273`) already count per-evaluation reasons, not one exclusive first rejection per closed bar. Multiple anchors, both directions, graph/OB scans and repeated evaluations can contribute; the bounded histogram recycles entries. `DiagPublishCoreState` (`:19661`) may publish the session's most frequent rejection, not necessarily the last bar's rejection. These numbers must not be summed as exclusive candidate outcomes; the current diagnostics do **not** meet the requested mutually consistent per-bar funnel.

The patch adds rate-limited EA heartbeat fields `signal_copy_failures` (failed six-buffer copy attempts; repeats may count) and `invalid_buffer_signals` (numeric invalid observations, deduplicated by existing seen keys or a bounded session ring), alongside the existing `expired` count. Heartbeat-window CopyBuffer failures are reported separately as not ready, not included in the six-buffer attempt count. They have different denominators and must not be added to indicator candidate counts. Counters for each of sweep, displacement, MSS/BOS, OB/FVG, TopDown, confidence, reliability, RR, causal invariant and CORE publication as a **single mutually exclusive per-candidate/per-bar ledger are NOT IMPLEMENTED**. A correct implementation needs explicit identity for each attempted candidate and selected/not-selected/lifecycle outcomes; using the existing histogram as a funnel would double-count and fabricate precision. That work remains open and needs deterministic runtime tests.
