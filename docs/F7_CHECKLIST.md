### 1.1 Before you press F7

1. **Copy the sources into the terminal you will test in.** The Data Folder
   (`File → Open Data Folder`) is what MT5 actually loads. A stale `.ex5` there
   makes every later observation worthless. Copy `MQL5/` over the terminal's
   `MQL5/`, or open the files directly from this checkout and note the path.
2. **Do not hand-fix a generated header.** `MQL5/Include/QSMC/QSMC_InputFingerprint.mqh`
   is generated by `tools/generate_input_fingerprint.py`. If it disagrees with
   `nadir2.mq5`, regenerate it in the repository and copy it — do not edit it in
   MetaEditor.
3. `nadir2.mq5` is CRLF and so are eight other files in the tree. MetaEditor
   does not care, but if you edit anything, do not let an editor normalise the
   endings — see the comment at the top of `.gitattributes`.

### 1.2 The compile order, and why this order

Open MetaEditor (**F4** from the terminal). For each file: open it, press **F7**,
read the **Errors** tab at the bottom.

Compile `nadir2.mq5` **first**. Everything else either reads its buffers through
`iCustom` or includes the same `MQL5/Include/QSMC/` headers, so a failure there
explains failures everywhere else.

Order: **1 → 2 → 3 → 5 → 6 → 7 → 8 → 9 → 4.**

### 1.3 Acceptance

**0 errors on every file.** That is the only gate.

Warnings are not a gate, but **paste them back anyway** — a warning about an
uninitialised variable or an implicit conversion in a 46,847-line file is the
kind of thing that is free to fix now and expensive to find later.

If a file fails: paste the **complete** Errors tab, not a summary. The line
numbers are the useful part, and this repository's line numbers are pinned by

### 1.5 Three attach-time behaviours added after the v6.6.25 handoff

All three come from the audit fixes in this branch and none existed when
`QSMC_V6.6.25_F7_AND_TESTER_HANDOFF.md` was written. None is an error — but if
you see one and do not know it is deliberate, it looks like a broken build.

**AUD-06 — a session window that cannot open now refuses the attach.** If
`InpSessionStartHour` or `InpSessionEndHour` is outside `0..23` the EA stops at
`OnInit` with:

```
[QSMC_AT] session hours out of range: 0 <= InpSessionStartHour <= 23 and
          0 <= InpSessionEndHour <= 23. Got <n> and <n>. A wrap over midnight is
          allowed (22 -> 6); an hour outside 0..23 is not, and Start == End
          switches the filter off.
```

Before the fix the EA started happily with a window no hour could satisfy and
then refused every signal for the whole session, with no line explaining why.
**Every preset shipped in `presets/` is in range** — measured: `10/18`, `10/18`,
`10/18`, `8/20`, and `0/0` (filter off) — so this only fires if you type an hour
in yourself.

**AUD-07 — a root that failed to initialise now says so.** If the arbitration
root cannot initialise (market-data failure or a failed `ConfigureStructure()`),
you will see one of:

```
[QSMC_ARB] root Init() failed - destroying the half-initialised root so the next
           attempt starts clean; arbitration is OFF for this instance
[QSMC_ARB] root create FAILED (AUD-07) - arbitration OFF for this instance;
           signals and buffers are unaffected
```

Arbitration is analytical, so this does **not** stop the indicator publishing
signals or filling buffers. Before the fix the same failure was silent and the
next attach reported success over a root that had never become ready.

**Sizing inputs — a multiplier the EA would have rewritten now refuses the
attach.** `InpWeakRiskMultiplier`, `InpModerateRiskMultiplier`,
`InpStrongRiskMultiplier` and `InpMaxAggregateRiskPercent` were the only risk
inputs with no attach-time check; each was clamped at use instead. A class
multiplier above `1.00` was capped to `1.00` in `CalcLots()`, so
`InpWeakRiskMultiplier = 3` sized a WEAK signal like a STRONG one and the only
trace was `risk_mult=1.00` in a per-signal line. Now:

```
[QSMC_AT] sizing inputs out of range: 0.00 <= InpWeakRiskMultiplier,
          InpModerateRiskMultiplier and InpStrongRiskMultiplier <= 1.00, and
          0.00 <= InpMaxAggregateRiskPercent <= 2.00% (HARD aggregate bound).
          Got <n> / <n> / <n> / <n>. A multiplier above 1.00 used to be capped
          to 1.00, so a WEAK signal was sized like a STRONG one; 0.00 stays
          legal (0 = that class is not executed, or the aggregate cap is OFF).
```

The bounds are the same numbers the enforcement already applied, so **no size
changed** — only the silent rewrite became a refusal. `0.00` stays legal for all
four because zero already means something (that class is not executed / the
aggregate cap is OFF). `InpRequireProfileMatch` is a `bool`, so there is no range
for it to fail. **All ten shipped presets load**: the four that set these inputs
use `0.25 / 0.50 / 1.00` with an aggregate cap of `1.00` or `0.50`. The REAL
profile's `InpRealMaxRiskPercent` and `InpRealMaxAggregateRiskPercent` are
**still** clamp-at-use only — see
[`EA_RISK_INPUTS.md`](EA_RISK_INPUTS.md) §5.

Record whichever of these you see in §10 of
[`F7_RESULTS_TEMPLATE.md`](F7_RESULTS_TEMPLATE.md), with the line verbatim.

### 2.1 What this plan is for

### 2.2 Fixed settings — identical in both runs

| Setting | Value | Why |
|---|---|---|
| Symbol | **XAUUSD** (your broker's own suffix) | the symbol the presets and the replay CSVs are written for |
| Timeframe | **M15** | the preset's designed timeframe; `InpExecTimeframe` and the whole causal chain assume it |

### 2.6 Then one input at a time

Runs A and B together cannot tell you whether all seven were needed or whether
one did all the work. So run seven more times, each starting from **Run A** and
changing exactly **one** input to its shipped value. Record line 1 and line 4 of
the table for each.

Without this pass, a relaxation that only ever fires on this one week is
indistinguishable from a general improvement.

### 2.7 The overfitting test

Repeat the A/B on **at least one other window** with a comparable vertical leg.
A change is a fix if it generalises to a market-structure class; it is a fit if
it only ever catches the 2026-11-27 leg.

### 2.8 What would count as validated

Not "more signals". A relaxation that doubles the count and halves the average
RR1 is worse. The acceptance evidence is all three of:

1. the 2026-11-27 leg appears in Run B and not in Run A;
2. the refusal histogram moves **on the keys the thresholds table names** — a
   count that moves elsewhere means a different gate was binding;
3. the added signals survive the entry review instead of being refused
   downstream.

## What this document deliberately does not claim

* It does not claim the source compiles. That is item 1 of the open register and
  only F7 can close it.
* It does not claim the shipped thresholds are better than the old ones. No
  measurement exists in either direction.
* It does not claim a win rate, a probability, or an expectancy. One week of one
  symbol cannot support any of them.
* It does not claim the two experimental programs of Part 4 belong to this
  release, work, or are safe to attach. They are listed so you can compile them
  and report a result, not because anything here depends on them.
* It does not describe live or real-account behaviour. Every preset here is
  demo-armed by default; arming REAL requires three separate confirmations that
  are re-verified before every order (`tools/test_execution_safety.py`, block D9).
